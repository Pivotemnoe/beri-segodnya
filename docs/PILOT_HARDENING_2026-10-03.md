# Изменения для учебного пилота - 03.10.2026

Статус: код подготовлен в `codex/pilot-hardening-20261003`. Этот документ не доказывает публикацию на рабочем сервере. Установка на телефон не выполнялась, Android SDK и эмулятор не устанавливались. Временные сценарии используют отдельные базы и нейтральные записи.

## Что изменилось

1. Общая обработка HTTP-ошибок и безопасная отдача файлов. Неверно закодированные cookie/ссылки и каталоги вместо картинки не останавливают сервер.
2. Условия новых броней сохраняются при создании, независимо от будущей правки предложения. Старым броням не придумывается исходная цена.
3. Коды проверяются на уникальность во всей базе, включая запасной и расширенный диапазон.
4. Один UUID-запрос можно повторить без второй брони и списания. Изменённые данные с тем же ключом отклоняются. Это не универсальная дедупликация человека/номера: новое намерение и новая страница могут создавать отдельный заказ.
5. Роль продавца с собственным логином: свои коды, цена, адрес/время и выдача/неявка; без телефона покупателя, приватной ссылки, профиля и публикации.
6. Адаптивные карточки, подтверждение конкретного кода, сохранение поиска, время обновления и сообщение о новой брони. Проверка каждые 15 секунд только при видимой вкладке, без push при закрытом кабинете.
7. Периоды результатов и `Выдано на сумму`, без подмены подтверждения платежа. Неизвестные суммы старых выдач исключены и отмечены отдельно.
8. Отдельная администраторская корректировка завершённого результата с причиной, сравнением ожидаемого статуса и записью сотрудника. Бронь не открывается заново, физический возврат еды не выдумывается.
9. UI-черновики разделены по магазину и сотруднику. Старый общий черновик не переносится автоматически.
10. Квоты фото 100 MiB на магазин / 2 GiB всего по умолчанию; полная проверка до записи. Достижение квоты ничего не удаляет.
11. Восстановление проверяет полную пару базы/фото и манифест до замены, требует заявления об остановленном сервере и сохраняет предыдущие данные.

## Команды проверки (Node 24.19.0)

```sh
npm run build
npm run test:security
npm run test:request-boundaries
npm run test:api
npm run test:backup
npm run test:upload-quota
npm run test:android-vulnerabilities
git diff --check
```

Build включает Android-config, хеш опубликованного APK и конфигурацию связки TWA/сайт. APK и signing key в этом этапе не менялись. Проверка установки, камеры, Back, возврата из фона и обновления установленного APK остаётся отдельной приёмкой на реальном устройстве.

Сценарии проверки: исходные падения до патча в одноразовых процессах; контролируемые ошибки и живой сервер после каждого запроса; принудительные ошибки открытия/чтения потока; обычные страницы, изображения, APK и загрузки; снимок после правки цены/времени/адреса/названия; коллизии и заполненный диапазон; повтор запроса; продавец/другой магазин; закрытые статусы; причина корректировки и остатки; повреждённые, отсутствующие, лишние и симлинк-фото; лимиты без частичной записи. Изменение пароля проверяется API-тестом, а не автоматической записью новых паролей через браузер.

В браузере проверяется реальный localhost-интерфейс. Узкая ширина 390 px - проверка адаптивности, не эмуляция Android и не приёмка устройства. Установленный клиент и рабочий сайт не изменяются до утверждённой выкладки.

## Результат повторной проверки

На итоговом коде прошли build (47 JS-модулей), security (210 файлов и runtime-контракты), request-boundaries (включая асинхронные ошибки файлов) и полный API smoke с pilot-hardening-сценарием. Backup smoke и upload-quota прошли на этом этапе отдельно; OSV не нашёл известных уязвимостей в 53 закреплённых Android release-зависимостях. Это не доказательство отсутствия всех возможных уязвимостей.

Smoke дополнительно компилирует именно отдаваемые `/app.js` и `/public.js`, а не только внешнюю JS-обёртку сервера. Отдельный тест проверяет первое/второе нажатия административной корректировки, сброс и истечение подтверждения.

В реальном браузере: продавец видит только разрешённые разделы; новая бронь поступает без перезагрузки; поиск и открытый черновик сохраняются; при ширине 390 px документ не шире экрана; выдача требует повторного нажатия по конкретному коду; публичная бронь показывает дату, цену, состав и аллергены. Административная поправка сначала показывает код/результат на кнопке, затем сохраняется с записью в журнал и пересчётом суммы. Обнаруженный при первом браузерном прогоне обход второго нажатия исправлен и повторно проверен. Ошибок/предупреждений в консоли итоговых страниц не было.

Все пользовательские сценарии использовали одноразовые учебные базы. Проверочные процессы и базы удаляются после проверки, APK не пересобирался, Android SDK/эмулятор не устанавливались. PDF-памятка обновлена отдельно; она предупреждает о необходимости рабочей выкладки до передачи персоналу.

## Порядок выкладки и возврата

1. Подтвердить разрешение на рабочее обновление и проверить, что рабочие файлы не разошлись с исходной версией. Не затрагивать другие приложения VPS.
2. Остановить только `beri-segodnya`, сохранить базу, фото и манифест, проверить их и архив предыдущего исходного релиза. Не выводить реальные пароли и данные клиентов в отчёт.
3. Выложить только утверждённую версию исходников/статических файлов, сохранить рабочие `.env`, `data`, `backups`, логи и signing key. Новые UI/серверные изменения не требуют нового APK.
4. Запустить тем же Node 24.19.0 в одном процессе. Проверить readiness, публичные страницы, Android-download и анонимный отказ приватных API. Реальную бронь и новых сотрудников без согласованных данных не создавать.
5. При проблеме вернуть предыдущие исходники. Данные назад не откатывать автоматически: после новых броней это потеряет записи. Если требуется восстановление данных - остановить все записи и отдельно согласовать точную проверенную пару.

## Что остаётся вне этого технического этапа

Рабочая выкладка до разрешения; установка APK на реальные телефоны; независимое юридическое согласование; реальные заведения/фото и обучение смены; внешнее хранилище резервных копий и проверка доставки оповещений (нужны согласованные получатель/место); миграция JSON на SQL перед ростом/несколькими процессами. Не запускать несколько экземпляров текущего JSON-сервера.

Инструкции: `OWNER_GUIDE.md` - владельцу сервиса, `PARTNER_QUICK_PUBLISH.md` - руководителю/менеджеру магазина, обновлённая PDF-памятка - сотруднику смены. Старый аудит от 02.10 сохраняется как исторический снимок, а не перезаписывается задним числом.
